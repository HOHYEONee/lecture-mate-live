# CLUE 개발 안내

온라인 강의의 실시간 맥락을 이해하는 멀티모달 AI 학습 파트너  
P-실무프로젝트 SW1분반 1조 · 통합 인터페이스 기준 v1.6 · 2026-10-31

이 문서는 팀원 모두가 **시스템의 데이터 흐름, 자기 모듈의 책임, 다른 모듈과 연결할 방식**을 먼저 이해하기 위한 안내서다. 구체적인 필드 정의와 예외 처리 규칙은 [상세 명세](interface_spec_v1.md), 실제 Python 클래스·메서드는 [공통 계약](contracts.py)을 따른다.

## 1. 시스템의 목적과 전체 흐름

강의 화면과 시스템 오디오를 로컬에서 수집하고, 사용자가 "이 그래프는 무슨 뜻인가요?", "아까 설명한 방법은요?"처럼 질문하면 **현재 화면·관련 과거 발화·대화 이력**을 함께 AI 모델에 전달해 답변한다. 강의 플랫폼의 자막/API에는 의존하지 않는다.

**실시간 수집**

1. 앱이 캡처 영역, 세션 ID, 공통 시계, 공통 작업 큐 및 세션 저장 폴더를 준비한다. `session_dir`는 프레임 처리와 맥락 관리 모두에 전달한다.
2. 프레임 처리는 1FPS 캡처 후 SSIM으로 신규 대표 프레임 저장 여부를 판단한다. 중복이면 이전 파일 경로를 재사용한다.
3. 음성 처리는 시스템 오디오를 **5초 주기(초기 1초 중첩)**로 전사하고 실제 발화 시각을 부여한다.
4. 두 모듈은 `FrameRecord`/`TranscriptSegment`를 공통 이벤트 큐로 전달한다.
5. 맥락 관리는 이벤트를 SQLite에 기록한다. 전사는 별도 백그라운드 RAG 작업에 전달해 청킹·임베딩하고, 생성 결과를 다시 SQLite에 저장한다.

**사용자 질문**

1. 앱이 질문 입력 시작과 전송 시점 화면을 각각 즉시 캡처하여 `QuestionRequest`에 포함한다.
2. 맥락 관리가 **이미 확정된 전사**·대표 프레임·Q&A 이력을 선택하고, 필요한 경우 RAG에 **키워드 + 의미 기반 하이브리드 검색**을 요청한다. 질문 때문에 미전사 오디오의 전사 완료를 기다리지 않는다.
3. 검색 결과의 시간 정보를 이용해 관련 과거 프레임을 선택한다.
4. AI 모델이 답변을 스트리밍하면 앱이 화면에 표시한다. 답변 처리 중에는 새 질문을 받지 않는다.

**정상 종료:** 새 수집 중지 → 이벤트 큐 비우기 → 남은 RAG 작업·청크 저장 → SQLite 커밋·닫기 → 종료.

## 2. 모듈 담당과 개발 완료 기준

| 모듈 | 담당 | 구현 책임 | 인수인계 산출물 |
|---|---|---|---|
| **프레임 처리** | 강호현 | 지정 영역 1FPS 캡처, P/C/R·SSIM 비교, 프레임 그룹·대표 기록, 유형 분류, 이미지 파일 보존, 질문 즉시 스냅샷 | `FrameProcessorAPI`, `FrameRecord`, 저장된 상대 이미지 경로 |
| **음성 처리 + RAG 엔진** | 심영진 | WASAPI Loopback, faster-whisper, 발화 시간·중복 전사 조정, 텍스트 청킹·임베딩, BM25+시멘틱 검색, 메모리 인덱스 복원 | `AudioProcessorAPI`, `TranscriptSegment`, `RAGIndexAPI`, `RAGChunkRecord`, `RAGSearchHit` |
| **맥락 관리 및 Q&A** | 김혜연 | SQLite 전체 메타데이터 및 단독 쓰기, 수집 이벤트 저장, RAG 비동기 호출·결과 저장, 맥락 검색/선택, GPT API, 답변 중단 처리 | `ContextQAAPI`, 저장 스키마, `AnswerEvent` |
| **앱 및 시스템 통합** | 신혜연 | PySide6 UI, 캡처 영역 선택, 세션·공통 시간, 스레드·큐·Qt Signal 연결, 질문 입력 잠금·중단, 일시정지·정상 종료·오류 표시 | `AppControllerAPI`, 실행 가능한 통합 앱 |

RAG는 별도의 다섯 번째 상위 모듈이 **아니다**. 구현은 음성 처리 담당 범위에 두되, **실행 요청과 DB 저장은 맥락 관리**가 담당한다. 데이터 저장 책임을 RAG 구현으로 옮기지 않는다.

### 프레임 처리 체크리스트

- [ ] `set_region()`으로 지정 영역을 받고, **UI 창의 크기·위치와 관계없이** 캡처한다.
- [ ] 정기 캡처마다 P(직전)·C(현재)·R(활성 대표)를 비교해 `NEW_GROUP` / `NEW_REPRESENTATIVE` / `REUSED`를 판정한다.
- [ ] 새 대표 이미지만 파일로 저장하고, 중복 관측은 기존 `frame_id`·`image_path`와 새로운 `capture_seq`·`timestamp_ms`를 전달한다.
- [ ] 과거 대표 프레임은 삭제하지 않는다. `Text` / `Visual` / `Unknown`으로 분류한다.
- [ ] `capture_now()`로 질문 시작/제출 스냅샷을 독립 캡처하고, 정기 P/C/R 상태는 건드리지 않는다.
- [ ] 공통 시계를 참조해 수집 순간에 타임스탬프를 기록하고, `pause()` 요청 시 새 캡처만 중지한다.

### 음성 처리 및 RAG 체크리스트

- [ ] 시스템 출력 오디오만 수집하고 확정된 전사를 `TranscriptSegment`로 전달한다.
- [ ] **5초 단위 정기 전사와 초기 1초 오디오 중첩**을 구현하고, 중첩 구간의 중복 발화를 제거한다.
- [ ] 전사 지연과 무관하게 실제 발화 시작·종료 시각을 보존하고, 청크 경계 중복을 조정한다.
- [ ] 질문 제출 시 미전사 오디오를 즉시 전사하는 별도 경로를 만들지 않는다. 미전사 데이터는 기존 정기 전사 경로로 계속 처리한다.
- [ ] **Whisper 오디오 청크**와 **RAG 텍스트 청크**를 분리해 설계한다.
- [ ] 1차 구현에서는 일반적인 텍스트 청킹·임베딩을 수행하고 DB를 직접 수정하지 않는다. 프레임 그룹 기반 청킹은 검색 성능이 부족할 경우에만 검토한다.
- [ ] `search()`에서 BM25 키워드 검색과 벡터 유사도 검색을 통합하고, 출처 발화 ID·시점을 반환한다.
- [ ] `start()`에서 저장된 임베딩을 복원하고 `flush_pending()`으로 종료 시 남은 청크를 처리한다.

### 맥락 관리 및 Q&A 체크리스트

- [ ] `FrameRecord`·`TranscriptSegment`를 SQLite에 기록하고, 같은 이벤트 재전송 시 중복 쓰기를 막는다.
- [ ] 실제 저장 이미지(`frames`)와 모든 캡처 관측(`frame_history`)을 별도로 기록한다.
- [ ] 전사 저장 후 RAG 인덱싱을 **별도 작업**에 맡기고 결과 청크·벡터를 SQLite에 저장한다.
- [ ] 과거 질문에는 RAG 검색 결과·시간을 사용해 관련 전사와 대표 프레임을 선택한다.
- [ ] 질문 시작/전송 프레임, 최근 10분 전사, 최근 대표 최대 8장, 최근 Q&A 5개 및 관련 후속 문맥을 조합한다.
- [ ] 질문에 이용하는 전사는 **질문 제출 이전에 발화한 확정 전사**로 제한하고, 미완료 전사나 RAG 인덱싱 완료를 기다리지 않는다.
- [ ] 스트리밍 답변·취소·오류 이벤트를 앱에 전달하고 미완성 답변은 추후 대화 맥락에서 제외한다.

### 앱 및 시스템 통합 체크리스트

- [ ] 모듈에 독립 작업 스레드와 `queue.Queue[IngestEvent]`를 주입하고 UI 메인 스레드를 막지 않는다.
- [ ] 하나의 `SessionClock`을 관리하고, 두 수집 모듈의 중지 확인 **이후** 시계를 정지한다. 중지 직전 수집된 데이터는 모두 처리한다.
- [ ] `IDLE → RUNNING → PAUSING → PAUSED → RUNNING`과 `STOPPING → IDLE` 전환을 관리한다.
- [ ] 질문 입력 첫 유효 문자·제출 시점의 `capture_now()`를 호출하고 `QuestionRequest`를 전달한다.
- [ ] 답변 생성 중 입력·재제출을 막고, 중단 후 취소 확인을 받아야 다시 질문할 수 있게 한다.
- [ ] 정상 종료 시 수집을 먼저 멈추고 잔여 큐·RAG 저장·DB 종료를 기다리며 오류를 사용자에게 표시한다.

## 3. 모듈 사이의 연결 원칙

| 경계 | 데이터/호출 | 방식 |
|---|---|---|
| 앱 → 수집 모듈 | `CaptureRegion`, `SessionClockView`, 프레임용 `session_dir`, 시작·일시정지·종료 요청 | Python 메서드 |
| 수집 모듈 → 맥락 관리 | `FrameRecord` 또는 `TranscriptSegment` | 공통 `queue.Queue[IngestEvent]` |
| 맥락 관리 ↔ RAG | `RAGIndexAPI` 인덱싱·검색·복원·flush | 백그라운드 Python 호출 |
| 앱 → 프레임 → 맥락 관리 | 질문 시작/제출 `FrameRecord` 2개를 포함한 `QuestionRequest` | 큐를 우회하는 직접 메서드 |
| 맥락 관리 → 앱 UI | `AnswerDelta` / `AnswerResult` / `AnswerCancelled` / `AnswerFailed` | 콜백 → Qt Signal |
| 전체 모듈 → 앱 | `ModuleError` | 오류 콜백 |

모듈 간 통신에 HTTP 서버를 만들지 않는다. 수집 모듈은 Qt를 직접 참조하지 않으며, 맥락 관리만 SQLite 메타데이터를 수정한다.

## 4. 공통으로 확정한 규칙

| 항목 | 적용 규칙 |
|---|---|
| 프레임 중복 | 매 캡처마다 `FrameRecord` 생성, **중복 이미지 파일은 생성하지 않음**. `frame_id`·경로는 기존 것 재사용 |
| 대표 프레임 | 그룹마다 여러 대표 기록 보존. 현재 활성 대표는 P/C/R 처리에서 사용, `FrameRecord`에 가변 플래그를 추가하지 않음 |
| 유형 | `Text` / `Visual` / `Unknown`; `Mixed`는 `Visual`에 통합 |
| 오디오 전사 | **5초 정기 전사 + 초기 1초 중첩**. 질문 시 미전사 오디오 우선 전사 없음. 잔여 오디오는 정기 처리 후 저장 |
| 시간 및 ID | 앱 소유 공통 시계 사용. `session_id`를 제외한 저장 식별자는 시간 기반 이름 + 충돌 방지 순번 권장 |
| 세션 저장 경로 | 앱이 `sessions/<session_id>/`를 생성해 프레임·맥락 모듈에 동일한 `session_dir` 전달. 프레임은 `frames/`, 맥락은 `metadata.db` 소유. 앱 UI에서 루트 변경 기능 없음 |
| 일시정지 | `pause()`로 새 수집을 먼저 멈춘 뒤 `SessionClock.pause()` 호출. 그 전까지 취득한 데이터는 정상 처리하며 별도 경계 객체는 사용하지 않음 |
| 검색 | 전문 용어 대응을 위한 **키워드 + 의미 검색**. SQLite 영구 저장 및 선택적 메모리 벡터 인덱스 |
| 질문 | 한 번에 하나만 처리. 중단은 AI 답변만 취소하고 수집은 계속 |
| 상태 | `IDLE`, `RUNNING`, `PAUSING`, `PAUSED`, `STOPPING`, `ERROR` |
| 종료 | 수집 중단 후 **남은 이벤트와 인덱싱을 처리**하고 DB를 커밋한 뒤 종료 |

## 5. 이번 회의에서 확인할 사항

아래는 구현 세부 선택 또는 후속 성능 검증이 필요한 사항이다. **확정 사항으로 취급하지 않는다.**

- [ ] **기본 하이브리드 검색 성능 측정:** 관련 전사 검색 성능이 부족할 때만 프레임 그룹 경계 기반 청킹을 후속 개선안으로 검토
- [ ] SSIM 임계값 및 `Text`/`Visual` 분류 기준
- [ ] **5초 전사 주기·초기 1초 중첩의 정확도·지연 측정:** 필요 시 10초 전사와 비교
- [ ] Whisper 모델, 임베딩 모델·텍스트 청크 길이·BM25+벡터 검색 결합 방식
- [ ] 초기 통합 테스트 담당 및 일정, 오류 복구·강제 종료 정책

## 6. GitHub와 Notion에 옮길 때

권장 GitHub 구조:

```text
interface_spec/
  README.md                # 첫 화면: 시스템 및 담당 범위
  interface_spec_v1.md     # 상세 동작·이벤트·상태 규칙
  contracts.py             # 공통 데이터/API 시그니처
  proposal_changes.md     # 원래 제안서와 차이
```

GitHub에서는 `README.md`부터 읽고 상대 링크를 따라가면 된다. Notion에는 이 README를 **첫 페이지**, 상세 명세와 변경 사항을 **하위 페이지**로 가져오는 구성을 권장한다. Notion에서는 GitHub 상대 파일 링크가 자동 연결되지 않을 수 있으므로, 업로드 후 실제 GitHub 파일 URL로 변경한다.

공통 계약의 **필드, Enum, 메서드 시그니처**를 변경할 때만 전체 팀과 먼저 합의한다. 모듈 내부 모델·임계값·UI 디자인은 담당자가 실험 결과에 따라 선택한다.
