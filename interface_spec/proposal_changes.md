# 기존 과제계획서 대비 설계 변경 사항

비교 기준: 2026년 P-실무프로젝트 과제계획서(제안서)와 CLUE 통합 명세 v1.6.  
목적: 제안서에서 실제 구현 명세로 넘어오며 **무엇이 바뀌었는지**, **무엇이 구체화됐는지**, **무엇이 아직 결정되지 않았는지**를 구분한다.

## 1. 실제 설계 변경 또는 추가 결정

| 주제 | 기존 제안서 | 현재 명세 v1.6 | 구분 |
|---|---|---|---|
| 과거 전사 검색 | Kiwi 형태소 분석과 BM25 기반 검색 중심 | **BM25 키워드 + 임베딩 의미 검색**을 결합한 하이브리드 RAG. 임베딩은 SQLite 저장·메모리 검색 가능 | **기능 확장** |
| RAG 구현 분담 | 음성 처리=오디오·STT, 맥락 관리=RAG 포함 맥락 선택·답변 | **음성 처리 담당 범위에 RAG 검색 엔진 구현 추가**. 실제 호출·SQLite 저장·답변 생성은 맥락 관리 | **책임 재분배** |
| 질문 시 최신 음성 처리 | 질문 전송 시 미전사 오디오를 우선 전사해 최신 발화를 반영 | **5초 단위 정기 전사(초기 1초 중첩)**로 변경. 질문에는 이미 확정된 전사만 사용하고, 강제 전사는 초기 구현에서 제외. 미전사 오디오는 계속 정기 처리 | **구현 단순화·즉시성 절충** |
| 프레임 유형 | `Text` / `Visual` / `Mixed` | `Text` / `Visual` / `Unknown`. `Mixed`는 의미 있는 시각자료가 있다는 점에서 `Visual`로 통합, 미분류 시 `Unknown` 허용 | **분류 단순화** |
| 데이터 전달 | 모듈 인터페이스를 통한 전달로 기술 | 정기 `FrameRecord`·`TranscriptSegment`는 공통 이벤트 큐, 질문 즉시 캡처는 `QuestionRequest` 직접 전달. Python 객체 기반 단일 프로세스 | **통합 방식 확정** |
| 세션·일시정지 | 시작·중지 UI 및 비동기 실행을 주로 설명 | 하나의 `SessionClock`, `PAUSING` 동안 수집 중지 확인, **중지 후 시계 정지**, 재개 시 동일 세션 유지, 6개 상태 정의 | **행동 규칙 추가** |
| 질문 중복 입력 | 질문·스트리밍 답변 기능을 기술 | 답변 생성 중 추가 질문 금지, 중단 버튼 누른 뒤 취소 완료 확인 시 새 질문 허용. 진행 중 수집은 유지 | **UI 동작 확정** |
| 종료 처리 | 수집 중지·오류 표시 중심 | 새 수집 중단 후 잔여 이벤트 큐, RAG 인덱싱·미완성 청크를 저장하고 SQLite 커밋 후 종료 | **신뢰성 요구 추가** |

## 2. 기존 설계를 구현 가능한 수준으로 구체화한 내용

아래는 제안서의 방향을 바꾼 것이 아니라, 구현 시 서로 충돌하지 않도록 **명세를 상세화**한 항목이다.

| 항목 | 제안서의 핵심 | 새로 명시한 계약 |
|---|---|---|
| 프레임 중복 제거 | 저장하지 않은 캡처 시점을 당시 활성 대표 ID와 연결 | 중복 시에도 **`FrameRecord`를 매번 발행**하며 기존 `frame_id`·`image_path`를 재사용. `capture_seq`와 취득 시각만 갱신 |
| 프레임 이미지 보존 | 모든 대표 프레임을 보존 | `frames`는 실제 이미지별, `frame_history`는 캡처 관측별 저장. 질문 스냅샷은 별도 파일로 저장 |
| 대표 프레임 관리 | 그룹 내 최신 활성 대표를 P/C/R의 R로 사용 | 활성 대표는 프레임 처리 로직에 필요하나 **`is_current_representative` 같은 가변 필드를 `FrameRecord`에 추가하지 않음** |
| SSIM 분기 | 직전 P/현재 C, 대표 R/현재 C 비교 | `NEW_GROUP` / `NEW_REPRESENTATIVE` / `REUSED` 및 질문 스냅샷 구분. P/C 비유사이면 새 그룹 생성 |
| 프레임·전사 동기화 | 공통 시간 정보로 결합 | 앱에서 생성한 공통 시계의 **실제 취득 시각** 사용. 처리 완료 시각을 타임스탬프로 사용하지 않음 |
| 자료 ID | 그룹·대표 프레임에 고유 ID | `session_id`는 별도 고유값, `frame_id`는 저장 이미지 ID라 중복 때 재사용, `capture_seq`는 관측별 유일. 시간 기반 이름은 충돌 방지 순번과 함께 사용 |
| 데이터 저장 | SQLite와 이미지 파일 | DB 쓰기는 맥락 관리가 전담. `frames`, `frame_history`, `transcripts`, `questions`, `answers`, `text_chunks`, `chunk_embeddings` 논리 테이블 |
| 세션 폴더 구조 | SQLite와 이미지 파일 분리 저장 | `sessions/<session_id>/frames/`와 `metadata.db`를 표준 구조로 확정. 앱이 생성한 같은 `session_dir`를 프레임·맥락 관리 모두에 전달 |
| RAG 결과 활용 | 과거 전사 시점을 검색해 관련 프레임 선택 | 검색 엔진은 `RAGSearchHit`에 원문·발화 ID·시점·점수를 포함하고, 맥락 관리가 이미지·Q&A를 결합 |
| Q&A 연속성 | 최근 5개 이력 + 같은 `category_id` | 동일 개념의 `context_tag`로 명명. 취소·실패 답변은 이후 Q&A 문맥에서 제외 |

## 3. 유지되는 핵심 목표

- 프레임 처리·음성 처리·맥락 및 Q&A·앱 통합의 **4개 상위 모듈** 구조
- Windows 데스크톱 앱, 지정 영역 **1FPS 캡처**, WASAPI Loopback·faster-whisper 기반 로컬 STT
- P/C/R·SSIM으로 프레임 그룹과 과거 대표 프레임 보존
- 질문 **입력 시작/전송 시점 프레임** 각각 확보, 최근 10분 전사, 최근 대표 최대 8장, Q&A 5개 + 관련 후속 문맥
- 프레임 최대 10장, 시간 정보로 연결하는 과거 맥락 선택, 멀티모달 AI 답변 스트리밍
- 4개 강의 영상 × 15문항 = 60문항 평가, 조건 A/B/C/D 비교, ALIVE 기반 Baseline·Hovie 비교
- 기존 제안서의 정량 목표(일반 질문 완전 정답률 80% 이상, 최신 반영 10초 이내, 첫 답변 중앙값 15초 이내 등)는 **변경하지 않음**

## 4. 제안서에 있으나 아직 공통 계약으로 확정되지 않은 사항

| 항목 | 제안서 | 현재 상태 및 후속 결정 |
|---|---|---|
| 형태소 분석 도구 Kiwi | BM25 검색 전 전처리에 사용 예정 | 하이브리드 RAG의 **구현 선택지**로 유지. 최종 토크나이저는 전공 용어·한국어 검색 실험 후 결정 |
| 프레임 그룹 기반 텍스트 청킹 | 제안서에 직접 명시되지 않음 | **1차 구현에서는 일반적인 텍스트 청킹 + 하이브리드 검색을 적용**. 관련 전사 검색 성능이 부족할 경우에만 후속 개선안으로 실험. 채택한다면 그룹 경계 전달 API가 필요 |
| 레이아웃 분류 방식 | PaddleOCR 계열을 후보로 기술 | Text/Visual만 구분하는 방향은 확정했으나 분류 알고리즘과 임계값은 시험 후 결정 |
| Whisper와 SSIM 세부 설정 | 기술 후보와 실험 방향을 기술 | **5초 정기 전사와 초기 1초 중첩**을 시작값으로 확정. Whisper 모델·중첩 적정성·SSIM 임계값·큐 크기는 정량 시험 후 확정 |

## 5. 팀 회의 결론 기록란

| 확인할 결정 | 결론 | 책임 모듈 |
|---|---|---|
| 5초 전사 주기·1초 중첩 성능 검증 | 초기 설정 채택, 정확도·지연 측정 후 조정 | 음성 처리 / 앱 |
| 기본 하이브리드 검색 성능 및 추가 청킹 개선 필요 여부 | 1차 검색 평가 후 결정 | 프레임 처리 / RAG 엔진 / 맥락 관리 |
| 인터페이스 코드·DB 스키마 통합 시험 순서 | 미정 | 전체 |
