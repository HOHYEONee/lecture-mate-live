# CLUE 모듈 인터페이스 명세 v1.6

**프로젝트:** 온라인 강의의 실시간 맥락을 이해하는 멀티모달 AI 학습 파트너  
**대상:** Windows / Python 3.11+ / PySide6 / 단일 프로세스 내 독립 작업 스레드  
**성격:** 4개 모듈의 통합을 위한 공통 계약 (알고리즘 구현 세부 사항은 각 담당자 재량)  
**함께 읽을 문서:** [팀 개발 안내](README.md) · [제안서 대비 변경 사항](proposal_changes.md) · [공통 Python 계약](contracts.py)

## 문서 읽는 순서

1. 프로젝트 전체 흐름과 개인별 구현 범위는 **[README.md](README.md)**에서 먼저 확인한다.
2. 여기서는 데이터 형식, 호출 방법, 세션 상태 및 종료 조건을 확인한다.
3. 실제 Python 클래스와 함수 시그니처는 **[contracts.py](contracts.py)**를 기준으로 구현한다.

**핵심 구분:** 프레임·음성 모듈은 데이터를 생성한다. 맥락 관리 모듈은 메타데이터 및 SQLite 저장을 총괄한다. 음성 처리 담당 범위에 포함된 RAG 엔진은 청킹·임베딩·검색을 구현하지만, DB 소유권과 AI 답변 생성은 갖지 않는다.

## 1. 역할 분담과 모듈 경계

| 모듈 | 담당 | 핵심 구현 범위 | 다른 모듈에 제공하는 결과 |
|---|---|---|---|
| 프레임 처리 | 강호현 | 1FPS 영역 캡처, P/C/R·SSIM, 유형 분류, 프레임 파일 관리 | `FrameRecord`, 즉시 스냅샷 |
| 음성 처리 및 RAG 검색 엔진 | 심영진 | WASAPI Loopback, faster-whisper, 발화 시간, 텍스트 청킹·임베딩·하이브리드 검색 | `TranscriptSegment`, `RAGChunkRecord`, `RAGSearchHit` |
| 맥락 관리 및 Q&A | 김혜연 | SQLite 단독 쓰기, 전 데이터 관리, RAG 작업 요청, 맥락 선택, AI 응답 생성 | 검색 맥락, `AnswerEvent` |
| 앱 및 시스템 통합 | 신혜연 | PySide6 UI, 공통 세션 시계, 이벤트 큐, 작업 스레드, 세션 제어·오류 표시 | `QuestionRequest`, UI 상태·세션 제어 |

- UI 창의 위치와 크기는 캡처 영역과 **독립적**으로 관리한다. 캡처 영역은 물리 화면 픽셀 좌표로 전달한다.
- 모듈들은 Python 객체와 공통 데이터 클래스로 연결한다. 내부 데이터 전달에 HTTP/REST 서버는 사용하지 않는다.
- 프레임·음성 코어는 PySide6를 import하지 않는다. Qt Signal은 앱 통합 계층에서 UI로 전달할 때 사용한다.
- `contracts.py`의 클래스 이름, 필드, Enum 값, Protocol 시그니처를 모듈 간 계약으로 사용한다.
- **상위 모듈은 4개로 유지한다.** RAG는 맥락 관리 모듈 내부에서 호출되는 독립 하위 구성요소이며, 별도 프로세스·HTTP 서버를 사용하지 않는다.
- **코드 구현과 데이터 관리 책임을 구분한다.** RAG는 검색·임베딩을 구현하고, 맥락 관리는 SQLite 쓰기와 전체 메타데이터를 관리한다.

## 2. 데이터·식별자·시간 공통 규칙

### 2.1 식별자

- **새 `start_session()` 호출:** 새 `session_id`와 새 `SessionClock`을 생성한다.
- **`pause_session()` → `resume_session()`:** 동일한 세션 ID와 시계를 유지한다.
- `frame_id`는 **저장된 이미지 파일**의 식별자다. 새 이미지를 저장할 때만 새 ID를 만들며, 중복 관측에서는 기존 ID를 재사용한다.
- `group_id`, `frame_id`, `segment_id`, `chunk_id`, `question_id`는 각 세션 내부에서 중복되지 않도록 발급한다. 이름은 **발생 시점의 `timestamp_ms`를 기반으로 하되 동시 발생에 대비한 고유 순번을 결합**하는 방식을 권장한다(예: `f12000_003`). `session_id`는 독립적인 고유 ID를 사용한다.
- `capture_seq`는 **캡처 관측 자체**의 고유한 일련번호다. 같은 `frame_id`를 재사용하더라도 `capture_seq`는 매번 새로 부여한다. 질문 스냅샷과 정기 캡처가 공유하는 카운터를 사용한다.
- `timestamp_ms`는 **고유키가 아니며**, 시간 검색 및 정렬에만 사용한다. 서로 다른 데이터에 같은 ms가 발생해도 정상이다.

### 2.2 단일 공통 시계

- 앱 통합이 **하나의 `SessionClock`**을 생성·제어한다. 프레임·음성 모듈은 읽기 전용 시간 참조를 공유한다.
- `timestamp_ms`, `start_ms`, `end_ms`는 **세션의 누적 수집 시간(ms)**이다. 사용자 일시정지 시간은 제외한다.
- 구현은 `time.monotonic_ns()` 기반 경과 시간을 계산하며, 1ms마다 변수를 증가시키는 타이머는 사용하지 않는다.
- Python `int`를 사용하되 외부 직렬화/DB 스키마에서는 64비트 정수 범위를 기준으로 한다.
- 데이터의 타임스탬프는 **실제 취득/발화 시각**이다. SSIM 처리 완료 시각이나 Whisper 전사 완료 시각으로 대체하지 않는다.
- Q&A 응답 지연(`elapsed_ms`, `first_response_latency_ms`)은 수집 시계와 별개로 **실제 단조 경과 시간**으로 측정한다. 사용자가 세션을 일시정지해도 API 지연 측정은 계속된다.

### 2.3 일시정지 및 재개

1. 앱이 `PAUSING` 상태로 전환하고 프레임·음성 수집 모듈에 각각 `pause()`를 요청한다.
2. 두 모듈은 **새 데이터 수집을 중단**한다. 중지 명령 직전까지 실제 수집된 데이터도 정상 처리하며 폐기하지 않는다.
3. 두 모듈의 수집 중지 완료가 확인되면 앱이 `SessionClock.pause()`를 호출하고 `PAUSED` 상태로 전환한다.
4. 재개 요청 중에는 `PAUSED`를 유지한다. 두 모듈의 `prepare_resume()`가 완료되면 공통 시계를 재개하고 각 모듈의 `resume()`을 호출한 뒤 `RUNNING`으로 전환한다.

**수집 중지와 수집 데이터 처리 완료는 별개다.** 일시정지 직전에 받은 오디오의 Whisper 전사는 일시정지 상태에서도 완료될 수 있고, 해당 전사 결과는 원래 발화 시각으로 저장한다. `pause()` 완료는 새 수집이 멈췄다는 뜻이며, 큐·전사·RAG 작업까지 모두 끝났다는 뜻이 아니다. 일시정지 시 새로 받은 데이터를 버리기 위한 별도 경계 객체나 오디오 자르기 규칙을 사용하지 않는다.

일시정지 버튼을 누른 시각과 수집이 완전히 중지된 시각 사이의 짧은 지연은 **정상 수집 시간에 포함**한다. 독립된 모듈별 시간 카운터를 생성하거나 일시정지 때 누적 수집 ms를 재설정하지 않는다. UI 메인 스레드는 모듈의 수집 중지 확인을 동기 대기하지 않는다.

## 3. 공통 데이터 계약

정확한 Python 정의는 동봉한 [`contracts.py`](contracts.py)를 단일 기준으로 삼는다.

| 계약 | 주요 필드 및 규칙 | 생산자 → 소비자 |
|---|---|---|
| `CaptureRegion` | `left`, `top`, `width`, `height`; 실제 데스크톱 픽셀, 음수 위치 허용 | 앱 → 프레임 처리 |
| `FrameRecord` | 세션/저장 이미지 ID, 캡처 고유 `capture_seq`, **현재 관측** `timestamp_ms`, 세션 상대 이미지 경로, `FrameType`, `FrameSource`, `group_id`, `FrameDecision` | 프레임 처리 → 맥락 관리 |
| `TranscriptSegment` | 세션/발화 ID, `start_ms`, `end_ms`, 확정된 `text` | 음성 처리 → 맥락 관리 |
| `RAGChunkRecord` | 청크 ID, 원문 구간, 출처 발화 ID, 텍스트, 임베딩 및 임베딩 모델명 | RAG 엔진 → 맥락 관리(저장) |
| `RAGSearchHit` | 검색 청크 ID, 원문 구간, 텍스트, 출처 발화 ID, 검색 점수 | RAG 엔진 → 맥락 관리(Q&A) |
| `QuestionRequest` | 세션/질문 ID, 질문 텍스트, 입력/제출 ms, 해당 시점의 `FrameRecord` 2개 | 앱 → 맥락 관리 |
| `AnswerDelta` | 질문 ID, 순서 번호, 추가된 텍스트 조각 | 맥락 관리 → 앱 |
| `AnswerResult` | 최종 답변, 연속도 태그, 제공한 자료 ID들, 첫 응답/완료 지연 | 맥락 관리 → 앱 |
| `AnswerCancelled` | 질문 ID, 부분 답변, 취소까지 경과 시간 | 맥락 관리 → 앱 |
| `AnswerFailed` | 질문 ID, 실패 코드·설명, 실패까지 경과 시간 | 맥락 관리 → 앱 |
| `ModuleError` | 모듈명, 오류 코드·설명, 복구 가능 여부 | 각 모듈 → 앱 |

### 3.1 프레임 세부 사항

- **매 캡처 결과를 `FrameRecord`로 전달한다.** 새로운 이미지라면 파일 저장을 완료한 후 전달하고, 중복이라면 새 파일 없이 기존 저장 이미지의 `frame_id`·`image_path`를 담아 전달한다. 실제 NumPy 배열이나 원본 스크린샷 바이트는 큐에 넣지 않는다.
- `FrameSource.PERIODIC`: 정기 1FPS 수집. `group_id`가 있고 P/C/R 비교 결과에 따라 이미지 저장 시 `NEW_GROUP` 또는 `NEW_REPRESENTATIVE`, **저장 생략 시 `REUSED`**를 사용한다. P와 C가 비유사하면 R과 C의 유사도와 관계없이 새 그룹(`NEW_GROUP`)을 생성한다.
- `FrameSource.QUESTION_START` / `QUESTION_SUBMIT`: 질문 시작/제출 시점의 즉시 캡처. `group_id=None`, `decision=QUESTION_SNAPSHOT`이며 정기 P/C/R 상태를 변경하지 않는다.
- `REUSED`는 **직전 캡처 P가 아니라, 실제 파일로 보존된 참조 프레임**의 ID·경로를 사용한다. `timestamp_ms`는 해당 파일의 최초 저장 시각이 아닌 **현재 캡처 시각**이다.
- `frame_type`은 `image_path`가 가리키는 저장 이미지의 유형을 나타낸다. 중복 시 새 캡처의 별도 분류 결과로 기존 이미지 메타데이터를 덮어쓰지 않는다.
- 정기 캡처의 중복과 달리 질문 시점의 즉시 스냅샷은 해당 시점의 화면을 독립 저장한다. 두 캡처 경로 모두 각각 고유한 `capture_seq`를 발급한다.
- 새로운 대표 프레임이 생성되더라도 이전 대표 프레임의 이미지 파일과 기록은 보존한다. 현재 활성 대표는 프레임 처리 모듈이 P/C/R 비교에 활용한다.
- 프레임 유형은 `Text`, `Visual`, `Unknown` 세 가지다. `Text`는 텍스트 중심, `Visual`은 그래프·표·그림 등 의미 있는 시각 자료가 포함된 프레임으로 분류한다. 기존 `Mixed`는 `Visual`에 통합한다. 작은 로고나 장식 요소만으로는 `Visual`로 분류하지 않는다.
- 즉시 캡처에서 분류가 아직 끝나지 않았다면 `Unknown`을 허용한다.

| 현재 캡처 ms | `capture_seq` | `frame_id` | `image_path` | `decision` | 새 파일 저장 |
|---|---|---|---|---|---|
| 1000 | 1 | `f000001` | `frames/f000001.jpg` | `NEW_GROUP` | O |
| 2000 | 2 | `f000001` | `frames/f000001.jpg` | `REUSED` | X |
| 3000 | 3 | `f000001` | `frames/f000001.jpg` | `REUSED` | X |
| 4000 | 4 | `f000002` | `frames/f000002.jpg` | `NEW_REPRESENTATIVE` | O |

### 3.2 음성 세부 사항

- **정기 전사 주기는 5초**로 시작한다. 오디오 청크는 초기 설정으로 직전 청크와 **1초 중첩**해 구성하며, 중첩 구간에서 반복 인식된 텍스트는 출처 시각을 기준으로 중복 반영하지 않는다. 중첩 길이와 전사 정확도는 통합 테스트로 검증한다.
- 음성 모듈은 실제 발화 시작/종료 ms가 있는 **확정 전사만** `TranscriptSegment`로 전달한다.
- Whisper 오디오 청크와 RAG용 텍스트 청크는 구분한다. 음성 처리의 출력은 확정된 `TranscriptSegment`이며, 텍스트 청킹·임베딩·검색은 별도 RAG 하위 구성요소가 수행한다.
- 음성 버퍼링/전사 지연이 있더라도 실제 오디오 취득 시점을 기준으로 상대 시간을 보정한다.
- **질문 제출 시 남아 있는 미전사 오디오를 별도로 전사하지 않는다.** 이미 확정된 전사만 질문 맥락으로 사용하고, 미전사 오디오와 처리 중인 정기 전사는 기존 수집·전사 흐름에서 계속 처리해 완료 후 SQLite에 저장한다. 이 정책 때문에 오디오 데이터 자체를 폐기하지는 않는다.
- 최신 발화 반영 지연은 청크 수집 대기 시간뿐 아니라 Whisper 처리·이벤트 저장 지연까지 포함하므로, **5초 주기만으로 최신 맥락 10초 이내 반영을 보장하지 않는다.** 실제 지연과 전사 정확도를 측정한다.

## 4. 데이터 저장 및 RAG 경계

```text
sessions/
  <session_id>/
    metadata.db
    frames/
      <frame_id>.jpg
```

- 앱은 세션 디렉터리를 만들고 `session_dir`의 절대 경로를 프레임 처리와 맥락 관리에 동일하게 전달한다. **`FrameProcessorAPI.start(session_id, session_dir, clock, output_queue, on_error)`**를 사용한다. 프레임 모듈은 전달된 `session_dir/frames/`에 이미지 파일을 저장한다.
- 기본 저장 루트는 프로그램 실행 시 작업 디렉터리의 `sessions/`이다. 앱 UI에서 저장 위치를 변경하는 기능은 초기 범위에 넣지 않는다. `SessionManager(sessions_root=...)`는 테스트·개발자 설정용이며, 루트가 달라져도 내부 구조는 동일하다.
- `FrameRecord.image_path`는 `frames/<frame_id>.jpg`와 같은 **세션 기준 상대 경로**이다.
- 맥락 관리 모듈만 SQLite 메타데이터 쓰기를 전담한다. 프레임·음성 모듈과 RAG 검색 엔진은 SQLite를 직접 수정하지 않는다.
- 권장 논리 테이블: `frames`, `frame_history`, `transcripts`, `questions`, `answers`, `text_chunks`, `chunk_embeddings`.
- `frames`는 **실제 저장된 파일별 1개 행**을 관리하며 `(session_id, frame_id)`로 식별한다. `REUSED` 수신 시 새 행이나 새 파일을 생성하지 않는다.
- `frame_history`는 **각 캡처 관측별 1개 행**을 관리하며 `(session_id, capture_seq)`로 식별한다. `timestamp_ms`, `frame_id`, `source`, `decision`, `group_id`를 기록하여 중복 관측 시각도 보존한다.
- 이미지 본체는 파일로 보존하고 SQLite에는 경로와 메타데이터를 저장한다.
- 음성 전사 원문·시간을 우선 저장한다. 맥락 관리 모듈은 전사 등록 뒤 RAG 인덱싱을 **별도 내부 작업**으로 요청하고, RAG가 돌려준 청크·임베딩을 SQLite에 기록한다.
- RAG 엔진은 **BM25 키워드 검색 + 의미 임베딩 검색**을 제공한다. 청크 크기·임베딩 모델·검색 점수 통합 방식은 RAG 내부 구현에서 결정한다.
- 초기 제안은 SQLite에 벡터를 영구 저장하고 NumPy 메모리 행렬로 정확 유사도 검색하는 방식이다. 별도 벡터 DB를 필수로 요구하지 않는다.
- 임베딩 처리가 늦은 최근 전사도 시간 기반 조회로 사용 가능해야 한다.

### 4.1 RAG 검색 API

RAG 엔진은 맥락 관리 내부에서 호출하는 `RAGIndexAPI`를 구현한다. **SQLite에 쓰거나 GPT를 호출하는 기능은 포함하지 않는다.**

| API | 입력 → 출력 | 책임 |
|---|---|---|
| `start(session_id, restored_chunks)` | 저장된 `RAGChunkRecord` 목록 → 없음 | 기존 청크·임베딩을 메모리 검색 인덱스로 복원 |
| `index_transcript(segment)` | `TranscriptSegment` → 새 `RAGChunkRecord` 0개 이상 | 텍스트 청킹, 임베딩 계산, 내부 검색 인덱스 반영 |
| `search(query, top_k, until_ms)` | 질문 문자열·검색 개수·시간 상한 → `RAGSearchHit` 목록 | 키워드+의미 검색을 수행하고 검색 점수 기준으로 정렬 |
| `flush_pending()` | 없음 → 남은 `RAGChunkRecord` 목록 | 종료 시 아직 완성되지 않은 텍스트 청크 확정 |
| `stop()` | 없음 → 없음 | RAG 인덱스 정리 |

- **인덱싱:** 맥락 관리가 전사를 SQLite에 저장한 뒤 백그라운드에서 `index_transcript()`를 호출한다. RAG가 반환한 청크·임베딩의 영구 저장도 맥락 관리가 담당한다.
- **검색:** 맥락 관리가 `search()`를 호출한다. 반환된 텍스트·출처 발화·시간 정보를 기반으로 프레임 및 Q&A 이력을 결합한다.
- **책임 경계:** RAG는 검색 결과까지만 제공하며, 최종 프롬프트 구성·이미지 선택·GPT 호출은 맥락 관리가 수행한다.
- **비동기 처리:** 인덱싱과 검색의 동시 수행을 지원하고, 전사 저장과 UI 응답을 차단하지 않는다. 청킹·검색 알고리즘은 RAG 내부 구현으로 둔다.
- `index_transcript()`의 텍스트 청크는 Whisper 입력 오디오 청크와 별개다. **1차 구현은 일반적인 텍스트 청킹과 하이브리드 검색을 우선 적용**하며, 프레임 그룹 기반 청킹은 기본 구현 범위에 포함하지 않는다.

**검색 성능이 부족할 때 검토할 대안:** 먼저 고정 길이 등 일반적인 텍스트 청킹으로 **BM25 키워드 검색 + 임베딩 의미 검색**을 구현하고 검색 성능을 측정한다. 관련 전사 검색 성능이 합의한 기준에 미달하는 경우에만 프레임 그룹 전환을 텍스트 청킹의 참고 경계로 활용하는 방식을 추가 실험한다. 이때 긴 그룹은 내부에서 분할하고, 짧은 그룹은 인접 문맥과의 결합을 검토하며, 그룹 종료 전에도 청크를 생성해 검색 지연을 방지한다. 이 대안을 채택할 경우 현재 전사만 입력받는 `RAGIndexAPI`에 그룹 경계 정보를 전달하는 방법을 별도로 합의한다.

## 5. 수집 이벤트 큐

**전달 구조:** 프레임 처리·음성 처리 → **공통 `queue.Queue[IngestEvent]`** → 맥락 관리.

| 이벤트 | 큐에 들어가는 내용 | 발생 조건 |
|---|---|---|
| 정기 프레임 관측 | `FrameRecord` | 매 정기 캡처 완료 시(신규 파일 저장 또는 기존 경로 재사용) |
| 전사 확정 | `TranscriptSegment` | 발화 구간·텍스트 확정 |

- 앱이 큐를 생성·주입하며 **초기 권장 `maxsize=1000`**이다. 실제 값은 테스트로 조정한다.
- 큐의 수신 순서와 실제 시간 순서는 다를 수 있다. 검색·정렬은 공통 타임스탬프를 사용한다.
- 큐 소비 작업은 SQLite에 빠르게 기록하고 다음 이벤트로 이동한다. **임베딩 작업을 큐 소비 스레드에서 직접 수행하지 않는다.**
- 맥락 관리 모듈은 RAG 작업 큐를 별도로 운영할 수 있다. 검색·임베딩은 `RAGIndexAPI`에 위임하며, 큐 구성은 맥락 관리 내부 구현으로 둔다.
- **데이터 이벤트를 조용히 버리지 않는다.** 큐 포화·저장 오류 시 앱에 `ModuleError`를 알리고 수집 중지/재시도를 제어한다.
- 중복 전송/재시도 시 `frames`는 `(session_id, frame_id)`, `frame_history`는 `(session_id, capture_seq)`, 전사는 `(session_id, segment_id)` 기준으로 중복 삽입을 방지한다. **같은 `frame_id`의 서로 다른 관측 기록을 삭제하거나 합치지 않는다.**
- 프레임·음성·맥락 모듈의 오류는 수집 큐가 아닌 별도의 `on_error(ModuleError)` 콜백으로 앱에 전달한다.

### 5.1 즉시 캡처의 별도 경로

- 질문 시점 스냅샷은 정기 수집 이벤트 큐를 기다리지 않는다.
- 앱이 프레임 처리 모듈의 `capture_now()`를 호출하고 완성된 `FrameRecord` 2개를 `QuestionRequest`에 **직접** 포함한다.
- 질문 스냅샷은 맥락 관리 모듈이 요청 수신 시 등록한다. 정기 큐로 동일 기록을 중복 전달하지 않는다.
- 프레임 메타데이터 등록은 기존 `frames` 기록을 활용하며, 해당 즉시 캡처의 `capture_seq`는 `frame_history`에 기록한다.

## 6. 사용자 질문 → AI 답변

1. 사용자가 질문창에 **첫 비어 있지 않은 문자**를 입력하면 앱이 `question_id`와 `input_started_ms`를 만들고 `capture_now(QUESTION_START)`를 호출한다. 포커스만으로 캡처하지 않는다.
2. 텍스트를 완전히 지워 질문 초안을 취소하면 `discard_question_draft()`로 표시한다. 제출하지 않은 임시 프레임의 정리 정책은 앱/프레임 담당자가 구현한다.
3. 사용자가 Enter/제출 버튼을 누른 **그 순간** `submitted_ms`를 기록하고 `capture_now(QUESTION_SUBMIT)`를 요청한다.
4. 두 즉시 캡처가 준비되면 앱이 `QuestionRequest`를 조립해 맥락 관리 `ask_async()`를 호출한다. UI 메인 스레드는 캡처 완료나 API 응답을 동기 대기하지 않는다.
5. 맥락 관리 모듈이 두 스냅샷을 등록하고, 필요하면 RAG 엔진 `search()`로 과거 전사를 검색한 뒤 최신·과거 전사, 대표 프레임, Q&A 기록을 선택한다. **전사 완료를 위해 질문 처리를 추가로 기다리지 않으며**, 이미 확정된 전사 중 질문 제출 시점 이전 발화만 사용한다. 임베딩 인덱싱 완료도 무기한 기다리지 않는다.
6. GPT API로 질문과 선택된 텍스트·이미지를 보내고 생성 중에는 `AnswerDelta`, 완료 시 `AnswerResult`를 콜백으로 전달한다.
7. 앱 통합은 이 콜백을 Qt Signal로 바꿔 UI에 표시한다. 맥락 관리 모듈이 Qt 객체를 직접 조작하지 않는다.

**기본 맥락 선택 정책(맥락 담당자 구현):** 질문 시작·제출 스냅샷 각 1개, 최근 대표 프레임 최대 8개, 최근 10분 전사, 최근 5개 Q&A 및 같은 연속도 태그. 과거 지시어는 전사 RAG 검색과 과거 시점 주변 프레임을 사용하며 `Visual` 우선 규칙을 고려한다. 구체적인 선택·중복 제거·토큰 예산은 담당 모듈 내부에서 구현한다.

### 6.1 질문 상태/중단

| 상태 | UI 질문 입력·제출 | 중단 버튼 |
|---|---|---|
| `READY` | 허용 | 숨김 |
| `GENERATING` | 금지 | 활성화 |
| `CANCELLING` | 금지 | 비활성화 |

- 한 세션에서 **동시에 생성 중인 질문은 최대 1개**다. 별도의 추가 질문 대기열은 만들지 않는다.
- 사용자가 중단을 누르면 앱이 `cancel_question(question_id)`를 호출한다. 해당 AI 응답 수신을 취소하며 **프레임·음성 수집은 계속된다.**
- `AnswerCancelled` 확인 후 `READY`로 돌아간다. 취소된 질문 ID에 대해 늦게 도착한 `AnswerDelta`/`AnswerResult`는 UI와 Q&A 이력에 반영하지 않는다.
- API/질의응답 실패 시 `AnswerFailed`로 해당 질문을 종료하고 `READY`로 복귀할 수 있어야 한다. 모듈 일반 오류는 별도의 `ModuleError`로도 전달할 수 있다.
- 이미 보여준 부분 답변은 `중단됨`으로 표시할 수 있으나, 미완성 답변은 추후 Q&A 맥락에서 제외한다.
- API가 서버 측 연산까지 즉시 취소한다는 보장은 없다. 중단은 앱의 수신/표시와 로컬 작업에 대한 최선 노력 취소를 뜻한다.
- 첫 응답/완료 지연은 별도 측정한다. `used_frame_ids`/`used_segment_ids`는 **모델에 제공한 자료** 목록이지 모델이 실제 활용했다는 검증은 아니다.

## 7. 상태 관리·정상 종료·오류

- 앱에서 `SessionState`를 관리한다. 세션 상태는 다음 여섯 가지만 사용한다.

| 상태 | 의미 |
|---|---|
| `IDLE` | 세션 미실행 또는 정상 종료 완료 |
| `RUNNING` | 화면·음성 수집 중 |
| `PAUSING` | 수집 모듈의 새 데이터 수집 중지 완료 대기(공통 시계는 계속 진행) |
| `PAUSED` | 일시정지 완료 또는 재개 준비 중 |
| `STOPPING` | 수집 중지 및 잔여 이벤트·RAG 작업 처리 중 |
| `ERROR` | 정상 실행을 지속할 수 없는 오류 |

- `RESUMING`, `STOPPED`는 별도로 사용하지 않는다. 재개 준비 중에는 `PAUSED`를 유지하고, 정상 종료 완료 시에는 `IDLE`로 전환한다.
- `STOPPING` 진입 후 신규 수집 및 질문 제출을 허용하지 않는다.
- 정상 종료: **수집 모듈 정지 확인 → 공통 이벤트 큐 잔여 데이터 DB 등록 → RAG 작업 큐 처리 및 `flush_pending()` 결과 저장 → RAG 엔진 정리 → SQLite 커밋·연결 종료 → 프로그램 종료**.
- 이벤트 소비자가 실패하면 오류를 기록하고 재시도/복구 정책을 적용한다. 무한 대기하지 않도록 앱에서 오류 및 중단 경로를 제공한다.
- 앱 중단 시 진행 중인 질문은 취소 요청하고 결과를 무시할 수 있도록 질문 ID를 유지한다. 종료 중 API 작업의 처리 정책은 통합 테스트에서 최종 확인한다.
- 질문 처리 중에도 정기 프레임·전사 수집은 계속 수행한다. 세션 일시정지와 **AI 답변 중단 버튼**은 서로 다른 동작이다.

## 8. 개발 전 통합 테스트 체크리스트

- [ ] `CaptureRegion(left<0, top<0, ...)` 등 다중 모니터 좌표 전달
- [ ] 정기 캡처가 P/C/R 상태를 갱신하고 질문 스냅샷은 갱신하지 않음
- [ ] `Mixed` 없이 `Text`·`Visual`·`Unknown`만 생성하고, 텍스트+의미 있는 시각 자료는 `Visual`로 분류
- [ ] 대표 프레임의 과거 버전 보존 및 동일 그룹 내 새 대표 추가
- [ ] 5시간 일시정지 후 재개해도 누적 수집 ms가 이어지고 ID 충돌이 없음
- [ ] 캡처 이후 늦게 처리된 전사도 실제 발화 타임스탬프로 정렬
- [ ] 5초 정기 전사·초기 1초 중첩을 적용하고, 중첩 구간의 동일 발화가 중복 저장·반영되지 않음
- [ ] 질문 제출 시 미전사 오디오를 기다리거나 강제 전사하지 않으며, 해당 오디오는 추후 정기 전사로 정상 저장됨
- [ ] 실제 최신 발화 반영 지연과 전사 정확도를 측정하고, 필요 시 5초·10초 주기를 비교
- [ ] 중복 프레임이 새 이미지 파일 없이 기존 `frame_id`·경로와 새 `capture_seq`·`timestamp_ms`로 전달됨
- [ ] 같은 `frame_id`의 여러 `frame_history` 행을 보존하고 재전송 시 관측 이벤트만 멱등 처리
- [ ] 질문 전송 시각의 즉시 프레임이 큐 지연과 무관하게 `QuestionRequest`에 포함됨
- [ ] 맥락 DB 등록과 임베딩 작업이 서로를 장시간 차단하지 않음
- [ ] `PAUSING` 동안 수집된 데이터도 보존하고, 수집 중지 확인 후 공통 시계가 멈추는지 확인
- [ ] 일시정지 중에도 이미 취득한 오디오의 전사가 완료되고 원래 발화 시간으로 저장되는지 확인
- [ ] 재개 준비 중 `PAUSED`, 정상 종료 후 `IDLE` 상태 전환 확인
- [ ] RAG 엔진이 생성한 청크·임베딩을 맥락 관리 SQLite에서 저장·복원함
- [ ] RAG 검색 결과의 출처 발화·시간을 이용해 맥락 관리가 과거 프레임을 선택함
- [ ] 검색 요청과 백그라운드 임베딩이 동시에 수행되어도 검색 결과 및 메타데이터가 일관됨
- [ ] `GENERATING` 동안 추가 질문 금지; 취소 완료 후에만 입력 재개
- [ ] 취소 후 늦게 도착한 답변이 화면/이력에 반영되지 않음
- [ ] 정상 종료에서 이벤트 큐·임베딩 큐가 처리되고 SQLite가 저장됨
- [ ] DB 저장 실패 또는 큐 포화 시 조용한 데이터 유실 없이 오류 처리

## 9. 구현 책임 밖의 권장 사항

- SSIM 임계값, Text/Visual 분류기, Whisper 모델, **초기 5초 전사 주기·1초 중첩의 성능 검증 및 미세 조정**, RAG 청크 크기·임베딩 모델·BM25/의미 검색 융합 알고리즘, UI 디자인은 각 담당자가 실험·선택한다.
